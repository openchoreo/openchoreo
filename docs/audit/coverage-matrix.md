## Known non-events

Cases where a real state-modifying request produces no audit event, or a diminished one, by design or by a documented, unfixed gap:

- **Reads are out of scope.** Every GET operation on both surfaces, and MCP's `initialize` session handshake.
- **A malformed path parameter never reaches audit on REST.** oapi-codegen's generated wrapper binds path params and returns 400 before `HandlerMiddlewares` run (`server.gen.go`), so a 400 from bad path binding is never audited.
- **`source_ip` is unobtainable for a direct (non-proxied) MCP client.** `RequestExtra` carries no `RemoteAddr`; only `X-Forwarded-For`/`X-Real-IP` from `Extra.Header` are available, and a direct client sets neither.
- **`X-Request-ID` and `source_ip` are both trusted from the client with no proxy check.** `X-Request-ID` is hardened to require a parseable UUID (falling back to a generated one, see `audit.RequestIDRejections`); `source_ip`'s `X-Forwarded-For`/`X-Real-IP` are taken at face value — deploy behind a proxy that strips or overwrites both if `source_ip` needs to be forensically trustworthy.
- **An invalid `scope` argument on a scope-collapsed MCP tool attributes the call to the namespace-scoped operation with `result: failure`** — the tool call itself errors before resolving a scope, so the event records the tool's default binding rather than the scope the caller asked for. Harmless (nothing is silently permitted), just a label to be aware of when reading a failure event's operation_id.
- **`pkg/mcp.NewSTDIO` registers no middleware** — neither audit nor the authz filter. Sound today (there is no HTTP request and so no identity to attribute an event to), and it has no production caller in this repo, but it is exported: whatever first wires MCP-over-stdio gets an unaudited mutating surface until that's addressed.
- **`?filterByAuthz=false` records a service-layer authorization denial as `failure`, not `denied`.** Opening a session with that query parameter skips the MCP authz filter entirely, so a refusal surfaces as a `services.ErrForbidden` returned from the handler rather than one of the filter's own sentinels — `classifyResult` has no way to tell that apart from an ordinary failure. A `results: [denied]` query on the read path silently misses these.
- **An HTTP-level 401 on `/mcp` emits nothing.** `NewUnauthenticatedMiddleware` is composed into `APIMiddlewares` for REST but not into the MCP handler chain (`cmd/openchoreo-api/main.go`), so an expired or missing token produces an `unauthenticated` audit event on REST and silence on MCP. `mcpaudit.classifyResult`'s `ErrNoSubject → unauthenticated` only covers a request that already passed HTTP auth and has no subject in its MCP session.
